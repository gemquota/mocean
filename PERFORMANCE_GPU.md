# Mocean Performance and WebGPU Compute Assessment

**Date:** 12 November 2026  
**Status:** Architecture assessment only. No renderer or simulation backend has been changed.

## Executive decision

Evaluate WebGPU as an optional acceleration path, not as a replacement for the live habitat yet. First establish a repeatable CPU/GPU frame-time baseline. The strongest eventual candidates are GPU-side model deformation/transform and visibility work, followed by a unified GPU terrain/render path. Moving the authoritative creature simulation to compute shaders is not recommended at the current population and architecture.

The live product is currently a hybrid: Canvas renders the habitat and most creatures; a separate Three.js r180 WebGLRenderer draws up to 72 naturalistic model instances. Terrain chunks are generated by two module workers, projected and rasterised into cached Canvas tiles. The simulation runs at a 60 Hz fixed step while the habitat renders at up to 24 Hz. There is no measured ordinary-hardware frame-time baseline yet.

## Workload assessment

| Workload | Current path | Compute-shader fit | Recommendation |
|---|---|---:|---|
| Schooling and behaviour | JavaScript, 60 Hz, spatial hash, species branches, prey/flee rules | Medium in theory; poor first migration | Keep CPU authoritative. Revisit only if profiling shows simulation dominates at much higher populations. |
| Terrain voxel sampling / dual contouring | Two Web Workers produce CPU mesh arrays | High parallelism, but output currently feeds Canvas projection/rasterisation | Defer until a GPU terrain renderer can consume GPU buffers directly. CPU readback would erase much of the benefit. |
| Terrain projection, triangle ordering and tile rasterisation | Main-thread JavaScript + Canvas 2D | High potential if the whole terrain pass moves to GPU | Prioritise renderer unification and depth correctness before implementing. |
| Creature model transforms and deformation | Up to 72 Three.js scene objects, per-instance JS transform/update | High potential at scale | Best first compute/TSL prototype. Keep CPU simulation state as input; do not read GPU results back each frame. |
| Visibility / LOD selection | CPU screen projection, sorting and selection | High potential for large model counts | Prototype GPU frustum/occlusion-independent culling after model data is batched. Current 72-model cap may make the gain modest. |
| Plankton / suspended particles | Small bounded Canvas layer | Technically straightforward, negligible current workload | Do not spend compute complexity on a few hundred particles. Reconsider if particle count and visual effects grow substantially. |
| Water absorption / post-processing | Not yet integrated as a full-screen GPU pass | High fit for fragment/compute-capable GPU pipeline | Implement as GPU material/post-process work when renderer integration is ready; compute shader is not automatically required. |

## Why not move the whole simulation to the GPU now?

- Behaviour is branch-heavy and species-specific, including prey selection, flee response, social groups, energy/state logic and terrain-contact exceptions.
- The rest of the application currently consumes live per-creature positions, velocities, headings, species and metrics on the CPU. Frequent GPU readback would introduce synchronization and transfer costs.
- GPU-resident simulation would require redesigning the data model, spatial-neighbour search, collision/contact path, debugging and deterministic tests together.
- At the configured 10–200 visible population, the current CPU spatial hash may be cheaper and easier to validate than a GPU port. This is a hypothesis to measure, not a performance claim.

## Recommended staged investigation

### G0 · Establish the baseline (required before GPU implementation)

Record on representative desktop and mobile-class hardware:
- startup and time-to-first-frame;
- fixed-step simulation time per frame, number of catch-up steps and candidate neighbour checks;
- Canvas render time, terrain draw/raster time, Three.js model sync time and Three.js render time;
- frame-time p50/p95 and dropped-frame rate over a fixed 60-second seeded run;
- memory/geometry counts, visible models, terrain chunks and worker queue depth.

Run population points 10, 50, 100 and 200 with the same seed, camera and duration. Report CPU and GPU timings separately where timer-query support permits. Do not infer GPU time from JavaScript wall-clock duration. Repeat warm runs and note browser, OS, GPU and power mode.

### G1 · Low-risk renderer-side prototype

Build an isolated WebGPU/Three.js TSL spike using representative Mocean models and the same camera. Compare:
1. current WebGLRenderer path;
2. WebGPURenderer with its compatible WebGL 2 fallback;
3. optional compute/TSL deformation and batched transform/culling.

The prototype must report the backend actually selected after renderer initialisation. Test a WebGPU-capable browser and a WebGL2-only fallback browser. Measure startup, CPU frame cost, GPU frame cost, model count and visual parity. Keep the live page unchanged.

### G2 · GPU-resident terrain only if justified

A GPU terrain path is worthwhile only if terrain extraction, projection, depth ordering and drawing can stay GPU-resident. Avoid generating a mesh on GPU, copying it to JavaScript, then sending it back to a renderer. Compare a direct GPU density/surface path with the existing worker-generated chunks, including chunk seams, contact-field parity and memory.

### G3 · Simulation compute only after evidence

If G0 shows simulation is the dominant bottleneck at the upper population range, prototype a narrow, deterministic kernel (for example broad-phase neighbour candidate generation or simple integration) against the CPU reference. Preserve CPU authority for behaviour/contact until the entire state pathway can remain resident without readback. Require trajectory-error bounds and regression comparisons before any adoption.

## Acceptance gates

No GPU path is adopted unless it:
- improves representative p95 frame time by at least 20% or provides a similarly material, measured capacity gain;
- does not regress low-end/WebGL2 fallback performance by more than 5%;
- preserves visible pose, depth ordering, terrain seams/contact and creature motion;
- has a graceful fallback when WebGPU is absent or device initialisation fails;
- avoids per-frame GPU-to-CPU readback on the hot path;
- passes automated parity tests and visual review.

These are proposed project gates, not measured results.

## Compatibility and maintenance risks

- WebGPU is not a universal browser baseline; feature detection and a real fallback are mandatory.
- Three.js WebGPURenderer uses the node-material/TSL path. Existing ShaderMaterial, RawShaderMaterial, onBeforeCompile modifications and EffectComposer effects are not drop-in compatible.
- WebGPURenderer may fall back to WebGL 2 for compatible renderer code, but WebGPU-only compute features cannot be assumed to work on that fallback.
- The live model overlay currently uses Three.js WebGLRenderer and GLTF-derived model instances. Renderer migration therefore needs a deliberate adapter and visual regression, not a constructor swap.
- Device loss, shader compilation latency, memory pressure, thermal throttling and mobile browser differences must be tested.

## Current outcome

**Recommendation: profile first, then prototype model deformation/transforms and culling.** Keep CPU simulation, current terrain workers and the live Canvas/WebGL path unchanged until measured evidence justifies a migration. No speedup is claimed by this assessment.
